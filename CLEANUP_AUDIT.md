# Homey — Cleanup Audit

Findings from a documentation and cleanup pass over this repository. This file is
a review checklist, not project documentation — `README.md` describes the
application itself and covers only code that is actively used.

Items marked ✅ have been resolved. Everything else is a candidate for review;
**nothing listed here has been deleted without being noted as such.**

### D. Unreferenced by application code (but unit-tested)

**Resolved — all three have been removed**, together with their test suites,
after verifying that every feature they once implemented is fully covered by the
live client/server code path. The record of what they were is kept below.

These were the original in-memory domain model, written before the backend
existed. They were *already* commented out of `App.tsx` in the first commit in
this repository (2025-11-12, "new improved homey with external database") — the
in-memory phase predates the git history entirely, and the database commit is the
moment they were retired.

They were nonetheless good code. `client/coverage/lcov.info`, committed in that
same first commit, records what their suites achieved when last run.

| Class | Line coverage | Function coverage | Tests |
|---|---|---|---|
| `ProfileManager.ts` | **100.0%** (99/99) | **100.0%** (32/32) | 53, active |
| `MatchingSystem.ts` | **100.0%** (77/77) | **100.0%** (28/28) | 48, **commented out** |
| `MessagingSystem.ts` | 95.2% (79/83) | 94.7% (18/19) | 49, active |
| `Group.ts` | 94.9% (93/98) | 91.4% (32/35) | 55, active |
| `User.ts` | 89.7% (61/68) | 92.6% (25/27) | 39, active |

Note the second row: `MatchingSystem` shows **100% coverage in the committed
report while its test file is fully commented out**. The report is a stale
snapshot taken before the suite was disabled — meaning those 48 tests did once
run and pass. Re-enabling them is likely a small job, not a rewrite.

**Why removal was the right call.** Before deleting, each feature these classes
once provided was traced end to end through the live code path, confirming a
complete implementation without them:

| Feature | UI (live) | API endpoint | MongoDB write |
|---|---|---|---|
| Messaging | `MessagingInterface.tsx`, `GroupManagement.tsx` | `POST /api/messages` | `new Message(...)` → `message.save()` |
| Message history | both of the above | `GET /api/messages/:conversationId`, `/api/messages/group/:groupId` | `Message.find(...)` |
| Profile editing | `Profile.tsx` → `authService.updateProfile` | `PUT /api/auth/me` | `User.findByIdAndUpdate(...)` |
| Group invites | `Search.tsx` | `POST /api/groups/:groupId/invite` | `new GroupMatch(...)` → `.save()` |
| Join requests | `GroupManagement.tsx` | `POST /api/groups/:groupId/join-request` | `GroupJoinRequest` |
| Matching | `SwipeCard.tsx` → `App.handleSwipe` | `POST /api/swipe` | `swipeactions.insertOne(...)`, `new Match(...)` |
| Discovery / matches | `App.tsx` | `GET /api/users/:id/potential-matches`, `/matches` | `User.find`, `Match.find`, `GroupMatch.find` |

Every feature is implemented server-side and persisted to MongoDB. The removed
classes duplicated this logic in browser memory, where it could not persist
anything, and no live file referenced them.

The cost of removal is the loss of ~150 unit tests over that in-memory model.
`User.test.ts` (39 tests) and `Group.test.ts` (55 tests) remain.

**Why `Group.ts` was kept when the other three were not.** It was examined on the
same terms and is, strictly, also unreachable from the application: group data
arrives from the API as plain JSON (`useState<any>`), no component constructs a
`Group`, and the rules are enforced server-side. Its single import in `App.tsx`
was never referenced and has been removed, so it is now reached only by its tests.

It is retained for two reasons the other three did not share:

1. **It is the only readable statement of the voting rules.** The server
   implements the same majority threshold spread across a schema field, a Map,
   and two endpoints; this class states it in one method that can be read in a
   minute — and the accompanying 55 tests pin the behaviour at the boundaries
   (single-member groups, re-votes replacing earlier ballots, the proposer's
   automatic yes).
2. **It carries the second-largest test suite in the repository.** Removing it
   would leave 39 tests total.

`User.ts` remains the only class the running application instantiates.

### E. Debugging scripts tied to one historic session

Each hard-codes ObjectIds, email addresses, or a group named `BING` from a local
database that no longer exists. They produce no output anywhere else and cannot
be re-run meaningfully. All are documented in place with what they were for.

**These are the fossil record of one debugging session.** A MongoDB ObjectId
encodes its creation time in its first four bytes, so the hard-coded ids can be
dated precisely. Eight of the ten were created inside a **75-minute window on
2025-12-01, 17:28–18:43 PST** — and the commit `Full group functionality fixed`
lands at **19:01 PST the same evening**, adding most of these scripts in the same
change:

| Time (PST) | Script | What it was doing |
|---|---|---|
| 17:28 | `debug_group_match.js` | Inspecting a single invitation |
| 17:28 | `debug_accept_group.js` | Walking the accept preconditions one by one |
| 17:57 | `test_alex_accept.js` | Replaying the full accept sequence by hand |
| 18:19 | `debug_group_invites.js` | Why is the invitation not appearing? |
| 18:25 | `check_alex_groupmatch.js` | Found it: accepted invitation, user not in group |
| 18:40 | `fix_alex_group_issue.js` | Repairing that one record |
| 19:01 | — | `detect_and_fix_orphaned_group_matches.js` generalises the repair; fix committed |

The bug they converged on is the one described under **Flow 3** above: the accept
endpoint marked the invitation `accepted` *before* completing the join, so any
later failure stranded the user with an invitation to a group they were not in
and could never see again. The fix was to reorder the endpoint so the invitation
is marked last. Read in sequence, these scripts are a legible record of that
diagnosis — which is an argument for keeping one or two of them, even though none
can be re-run.

The two older ids are unrelated: `debugPotentialMatches.js` / `testApiDirectly.js`
reference a user created 2025-11-12, and `debug_accept_group.js` /
`debug_group_swipe.js` one from 2025-11-19.

**On the `BING` group.** Four scripts — `debug_alex_group.js`,
`debug_all_users.js`, `debug_group_invites.js` and `notify_group_update.js` —
each contain the line:

```js
const bingGroup = await Group.findOne({ name: 'BING' });
```

`BING` is **not** an identifier, constant, enum value or schema field. It is a
*data value*: the name a developer happened to type when creating a test group in
their own local database. The application never creates, seeds or looks for a
group by that name — a search of `server/index.js`, `server/models/`,
`server/routes/`, `server/middleware/` and all of `client/src` returns zero
matches. It is not in `seed.js` or `createUsers.js` either.

Nor does it appear in the committed server logs, which do record the group names
that really existed during those captured sessions (`BEST GROUP`,
`Alex Thompson & Steph C`, `group with members`). So `BING` predates even those
logs.

The practical consequence: on any database other than the one it was typed into,
`findOne({ name: 'BING' })` returns `null`, the surrounding `if (bingGroup)`
block is skipped, and that portion of the script silently prints nothing. The
scripts do not error — they just do less than they appear to. This is why they
are listed as dead weight rather than as broken code.

Note that `debug_alex_group.js` and `debug_all_users.js` each have a *second*,
generic half that works against any database, so removing only their `BING`
blocks would leave two useful diagnostics behind.

> **A trap to be aware of if you do remove them.** Deleting the `BING` block from
> `debug_alex_group.js` makes `require('./models/Group')` look unused — but
> removing it breaks the script:
>
> ```
> MissingSchemaError: Schema hasn't been registered for model "Group".
> ```
>
> Its `.populate('groupId')` call resolves `GroupMatch`'s `ref: 'Group'`, and
> Mongoose can only do that if the Group model has been **registered** by being
> required somewhere. In Mongoose, a model import can be load-bearing without
> ever appearing by name.
>
> This is independent of whether MongoDB is running: model registration happens
> in-process at `require` time, with `mongoose.connection.readyState` still `0`.
> It is, however, *latent* — with MongoDB down you hit
> `MongooseServerSelectionError: connect ECONNREFUSED 127.0.0.1:27017` at the
> `connect()` call first and never reach the query. The schema error only
> surfaces once a connection succeeds.
>
> The same trap already bites elsewhere: **`server/cleanup_stale_group_matches.js`
> calls `.populate('groupId userId')` without importing Group, so it crashes on
> its first query.** One-line fix, documented in that file's header.

> ⚠️ **Bug worth fixing before use:** `cleanup_orphaned_accounts.js` builds its
> "empty/orphaned groups" query as `$nin: [validUserIds]` — the id array nested
> inside another array. That tests whether `memberIds` equals that single array
> rather than whether its members are valid, so effectively **every group
> matches** and confirming the prompt deletes all of them. Verify the reported
> group count before answering `yes`.

### G. Not dead, but flagged during the pass

- `server/testUnmatchFunctionality.js` — named as a test but has no assertions and
  is not run by any runner. It writes to whatever database it is pointed at,
  using two arbitrary real accounts. Useful, but do not run it against data that
  matters.
- `server/Dockerfile` — has not been exercised since deployment moved to Railway
  and Nixpacks. Its `WORKDIR /app/server` does not match what the `COPY` steps
  create, and `npm ci --only=production` omits the devDependencies the client
  build needs. Either fix it or remove it in favour of `railway.json`.
- Root `package.json` — its single dependency (`node-fetch`) exists only for
  `tmp_accept_request.js`. Removing that script makes this file redundant too.
